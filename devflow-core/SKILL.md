# /devflow-core — 开发工作流（devflow 家族·开发变体）

本工作流是 devflow 家族的开发变体，集成了公共骨架和开发特有逻辑。

## 角色与约束

- 本对话窗口 = **总指挥**：只负责编排、汇总、核对，不写业务代码。
- 子智能体 = 执行者：必须返回**结构化摘要** `{完成项, 测试证据, 未完成项, 风险}`，禁止长篇工作汇报；总指挥只收摘要。
- **上下文管理**：系统会自动 compact，总指挥不手动触发；每阶段结束把关键状态追加到 `docs/plan/<task>.status.md`。

## 命名约定

- 启动阶段（0/1）确定 `<task>`（短横线英文 slug，如 `user-auth`），后续所有产物路径必须沿用，不得各自起名。

## 阶段

### 0. 任务分级与分类（启动先判断）

- 启动后立即按 **①请求类型 → ②影响面 → ③预估工时** 三级判断，自主裁剪，不机械跑完整流程：
  1. **分类请求**：Bug 修复 / 功能开发 / 优化 / 重构 / 纯文案·构建。
  2. **跨模块判断**：同一持久化资源多写入入口、状态跨 API/缓存/后台任务传播、涉权限/密钥/Agent/Skill/MCP、涉 Web/桌面/部署多端 → 判为跨模块。
  3. **定档 S/M/L**：S ≤30 分钟·单模块；M 半天内·1~3 模块；L 跨模块/涉数据迁移/权限/新 API/多天。
- 分类决定裁剪路径：
  - **Bug** → 复现测试 → 最小修复短路径（跳过完整拷问/调研/规划）。
  - **纯文案/构建** → 不建需求记录，直接做。
  - **S** → 跳过：拷问、技术调研、规划、并行执行、TDD 完整循环。
  - **L** → 全部阶段，TDD strict，强制调研与规划。
- 分级结果与裁剪理由写入 `docs/plan/<task>.status.md`；后续各阶段按此档位执行。
- 有疑问（分类/跨模块拿不准）再问用户，能自主判断的不问。

### 1. 需求对齐 — grill-me

- 调用 `grill-me`（grilling 会话）**一次对齐全部事项**，不遗留到实现期：
  1. 需求逐条确认：目标、范围、验收标准；
  2. **潜在问题对齐**：需求与现有代码/文档的匹配度、需求不完善处、关联小 bug、边界与失败场景、未知项；
  3. 多方案时给出可选方案与推荐项。
- S 级跳过拷问直接写 `docs/requirements/<task>.req.md`（仍须含需求清单 + 已对齐问题清单）；纯文案/构建可省。
- 产出需求文档；**向用户确认后**才进入下一阶段。

### 2. 规划 — Plan 智能体（含按需技术调研）

- **2.0 技术调研（按档位子步骤）**：L 级强制，M 级在技术方案不确定时执行，S 级跳过。用 **Firecrawl 搜索**设计方案/最佳实践 → 用 **Context7 查询**备选方案当前文档 → 对比给出推荐与取舍，写入计划。目的：决策贴合实际，避免返工。
- 用 Agent 工具调用 **Plan 智能体**，以需求文档为输入产出实施计划，保存 `docs/plan/<task>.plan.md`。
- 计划必须含**变更清单**（要动的文件/模块）与**验收标准**。
- 涉及数据/权限/API 结构变更时，计划须附书面方案（现状、模型、迁移与回滚）供用户确认后实施。
- 范围控制：只实现计划内内容；计划外一律保持现状。交付阶段用变更清单核对实际 diff。

### 3. 并行执行 — 项目级智能体

- 将计划按模块拆分任务。
- 默认直接手写 `项目/.claude/agents/*.md`（每个模块一个，20 行内）；**仅当**智能体需跨平台复用或含脚本/eval 时才调用 `agent-skill-creator`。
- 用 Agent 工具并行派发，要求每个子智能体**只返回结构化摘要**。

### 4. 实现（按级 TDD）

- 按阶段 0 的分级选择 `tdd-workflow` 强度：
  - **L（strict）**：完整 TDD 循环 — RED 实测 → 最小实现 GREEN → 重构 → 覆盖率 ≥80% → Git checkpoint → 写 TDD 证据报告 `docs/testing/<task>.tdd.md`。
  - **M（standard）**：RED 实测 → GREEN → 重构 → 覆盖率记录（不强制 80% 门槛）→ 精简版证据报告。
  - **S（light）**：仅新行为核心测试先行 + 现有测试回归通过；不强制 RED 证据与覆盖率报告。
- 证据须记录实际执行的命令与输出，不得虚构 RED/GREEN 结果。

### 5. 无独立审查

- 开发变体不设独立代码审查阶段；实现直接进入阶段 6（testing-quality-agent 全量测试）。

### 6. 测试 — testing-quality-agent

- 用 `testing-quality-agent` 做全量测试与质量门禁（lint / typecheck / format / coverage）。
- 门禁未过 → **停下，向用户报告，不擅自放行**。

### 7. 合规核对

- **代码 vs 规范**：用审查智能体把实际 diff 与规范文档（CLAUDE.md / AGENTS.md / PRD / 技术设计）逐条核对；不一致 → 修正并同步文档；无法单方修正 → 停下问用户。
- **工作流本身是否被遵守**（可选）：`skill-comply` 反查本流程/skill 是否被严格执行。它**不审查代码**，且每次要另起多个 headless `claude -p` 会话（成本高），默认**不**每次运行，仅定期或按要求手动跑。

### 8. 交付核对 — gate

- 用计划变更清单核对实际 diff：计划外改动一律回滚或经用户批准。
- 汇总交付物、剩余风险、未完成项。**未经验证不声称完成。**

## Gate 规则（全程）

- 每个阶段验收不通过 → **停下，向用户报告原因与选项**，不得"尽力继续"。
