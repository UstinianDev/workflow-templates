# devflow-base — 公共流水线骨架

这是 devflow 家族（`/devflow`、`/devflow-refactor` 等）的公共骨架。具体工作流先读取本文件，再按各自差异执行。

## 角色与约束

- 本对话窗口 = **总指挥**：只负责编排、汇总、核对，不写业务代码。
- 子智能体 = 执行者：必须返回**结构化摘要** `{完成项, 测试证据, 未完成项, 风险}`，禁止长篇工作汇报；总指挥只收摘要。
- **上下文管理**：系统会自动 compact，总指挥不手动触发；每阶段结束把关键状态追加到 `docs/plan/<task>.status.md`。

## 命名约定

- 启动阶段（0/1）确定 `<task>`（短横线英文 slug，如 `user-auth`），后续所有产物路径必须沿用，不得各自起名。

## 阶段

### 0. 任务分级与分类（启动先判断）

- 启动后立即按 **①请求类型 → ②影响面 → ③预估工时** 三级判断，自主裁剪，不机械跑完整流程：
  1. **分类请求**：Bug 修复 / 功能开发 / 优化 / 重构 / 纯文案·构建。
  2. **跨模块判断**：同一持久化资源多写入入口、状态跨 API/缓存/后台任务传播、涉权限/密钥/Agent/Skill/MCP、涉 Web/桌面/部署多端 → 判为跨模块。
  3. **定档 S/M/L**：S ≤30 分钟·单模块；M 半天内·1~3 模块；L 跨模块/涉数据迁移/权限/新 API/多天。
- 分类决定裁剪路径：
  - **Bug** → 复现测试 → 最小修复短路径（跳过完整拷问/调研/规划）。
  - **纯文案/构建** → 不建需求记录，直接做。
  - **S** → 跳过：拷问、技术调研、规划、并行执行、TDD 完整循环。
  - **L** → 全部阶段，TDD strict，强制调研与规划。
- 分级结果与裁剪理由写入 `docs/plan/<task>.status.md`；后续各阶段按此档位执行。
- 有疑问（分类/跨模块拿不准）再问用户，能自主判断的不问。

### 1. 需求对齐 — grill-me

- 调用 `grill-me`（grilling 会话）**一次对齐全部事项**，不遗留到实现期：
  1. 需求逐条确认：目标、范围、验收标准；
  2. **潜在问题对齐**：需求与现有代码/文档的匹配度、需求不完善处、关联小 bug、边界与失败场景、未知项；
  3. 多方案时给出可选方案与推荐项。
- S 级跳过拷问直接写 `docs/requirements/<task>.req.md`（仍须含需求清单 + 已对齐问题清单）；纯文案/构建可省。
- 产出需求文档后自动进入下一阶段；文档留在 `docs/requirements/` 供事后审阅。

### 2. 规划 — Plan 智能体（含按需技术调研）

- **2.0 技术调研（按档位子步骤）**：L 级强制，M 级在技术方案不确定时执行，S 级跳过。用 **`crw search`** 搜索设计方案/最佳实践 → 用 **`npx @arabold/docs-mcp-server@latest search`** 查询已索引的库文档（未索引时先用 `scrape` 建立索引）→ 对比给出推荐与取舍，写入计划。目的：决策贴合实际，避免返工。

**搜索工具自动索引规则**（全程生效）：
- 使用 `docs-cli` 搜索前，先运行 `npx @arabold/docs-mcp-server@latest list` 检查目标库是否已索引。
- 若未索引，**立即执行** `npx @arabold/docs-mcp-server@latest scrape <库名> <文档URL> --max-pages 100 --max-depth 3` 建立本地索引，再进行搜索。
- 使用 `fastcrw-skill` (`crw`) 时，若目标网站需要深度爬取，用 `crw crawl` 建立本地缓存供后续使用。
- 索引完成后记录到 `docs/plan/<task>.status.md`，避免重复索引。
- 用 Agent 工具调用 **Plan 智能体**，以需求文档为输入产出实施计划，保存 `docs/plan/<task>.plan.md`。
- 计划必须含**变更清单**（要动的文件/模块）与**验收标准**。
- 涉及数据/权限/API 结构变更时，计划须附书面方案（现状、模型、迁移与回滚）；方案写入计划后自动实施。
- 范围控制：只实现计划内内容；计划外一律保持现状。交付阶段用变更清单核对实际 diff。

### 2.5 前端设计规则加载（涉 UI 时执行）

当需求涉及前端/UI 时，在进入实现前执行：

1. **扫描项目级 AGENTS.md**：读取 `项目/.claude/AGENTS.md` 中的设计规则模块（如有），作为本次设计的硬性约束。
2. **激活 ui-ux-pro-max-skill**：调用 `/ui-ux-pro-max` 获取设计智能（配色、排版、动效、无障碍、响应式）。
3. **组件库文档查询**：用 `npx @arabold/docs-mcp-server@latest search` 查询已索引的 **Aceternity UI**（`ui.aceternity.com`，React/Next.js 动效组件）和 **IKun UI**（`ikun-ui.netlify.app`，Svelte/UnoCSS 组件）文档，按需求场景选型。未索引时先用 `scrape` 建立索引。
4. **设计氛围锚点**：以「《黑客帝国》— 编程语言是用来思考的」为设计精神内核，追求极客美学：深色系、高对比、代码感、赛博朋克气质。

产出：设计决策摘要写入 `docs/plan/<task>.design.md`，含组件选型、配色方案、动效策略。实现阶段必须遵循。

### 3. 并行执行 — 项目级智能体

- 将计划按模块拆分任务。
- 默认直接手写 `项目/.claude/agents/*.md`（每个模块一个，20 行内）；**仅当**智能体需跨平台复用或含脚本/eval 时才调用 `agent-skill-creator`。
- 用 Agent 工具并行派发，要求每个子智能体**只返回结构化摘要**。

### 4~5. 核心实现阶段（差异点）

- 由具体工作流覆盖：实现方式、是否强制 TDD、是否插入代码审查。
- **档位传递**（公共规则）：总指挥调用被调 skill（如 `tdd-workflow`、`code-refactor-master`）时，必须把档位显式写入调用指令（如「S 级 / light 测试」）；被调 skill 按档位分支执行，无档位参数时按 standard。
- **TDD 三档**（变体引用时保持一致）：
  - **L / strict**：完整循环 RED → 最小实现 GREEN → 重构 → 覆盖率 ≥80% → Git checkpoint → 写证据报告。
  - **M / standard**：RED → GREEN → 重构 → 覆盖率记录（不强制 80% 门槛）→ 精简证据报告。
  - **S / light**：仅新行为核心测试先行 + 现有测试回归通过；不强制 RED 证据与覆盖率报告。

### 6. 测试 — testing-quality-agent

- 用 `testing-quality-agent` 做全量测试与质量门禁（lint / typecheck / format / coverage）。
- 门禁未过 → **停下，向用户报告，不擅自放行**。

### 6.5 模块连通性验证

- **目的**：确保变更后的模块之间调用链路通畅，接口契约一致，数据流完整。
- **触发条件**：M/L 级强制；S 级仅当涉及跨模块调用时执行。
- **执行步骤**：
  1. **识别调用链**：分析本次变更涉及的模块，梳理所有跨模块调用关系（函数调用、API 请求、事件订阅、数据流传递），输出调用链清单。
  2. **逐链验证**：
     - **接口契约**：调用方使用的函数签名/请求参数/事件名与被调用方定义一致。
     - **数据格式**：传递的数据结构（字段名、类型、必填/可选）两端匹配。
     - **错误处理**：被调用方抛出的异常/错误码，调用方有对应处理路径。
     - **版本兼容**：涉及外部依赖或 API 版本时，确认向后兼容。
  3. **输出连通性报告** `docs/plan/<task>.connectivity.md`：每条链路的状态（✅ 通畅 / ⚠️ 风险 / ❌ 断裂），断裂链路必须修复后才能进入交付。
- **修复策略**：能自动修复的直接修（签名不匹配、缺少错误处理）；需设计决策的（数据格式变更、接口重构）停下问用户。
- **与测试的关系**：测试覆盖的是单模块行为正确性，连通性验证覆盖的是模块间契约一致性，二者互补不可替代。

### 7. 合规核对

- **代码 vs 规范**：用审查智能体把实际 diff 与规范文档（CLAUDE.md / AGENTS.md / PRD / 技术设计）逐条核对；不一致 → 修正并同步文档；无法单方修正 → 停下问用户。
- **工作流本身是否被遵守**（可选）：`skill-comply` 反查本流程/skill 是否被严格执行。它**不审查代码**，且每次要另起多个 headless `claude -p` 会话（成本高），默认**不**每次运行，仅定期或按要求手动跑。

### 8. 交付核对 — gate

- 用计划变更清单核对实际 diff：计划外改动一律回滚或经用户批准。
- 汇总交付物、剩余风险、未完成项。**未经验证不声称完成。**

## Gate 规则（全程）

- 每个阶段验收不通过 → **停下，向用户报告原因与选项**，不得"尽力继续"。
